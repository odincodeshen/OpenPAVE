# OpenPAVE v1.8.5 — A late renewal can no longer restart a motion

**Date:** 2026-10-11 · **Tag:** `v1.8.5`

A patch release on [`v1.8.4`](v1.8.4.md) that closes the known limit `v1.8.4` documented: renewing a body's
motion lease was done by re-sending the same motion, and a body cannot tell that apart from a new command.

## The bug

The body-side dead-man lease (`v1.8.2`) stops a `trot` / `move` the brain stops renewing. The brain renewed by
re-sending the same motion. If the lease had already run out and the body had stopped itself, the next
"renewal" was just a `trot` to the body — and it started marching again, with no decision behind it. Two
situations hit this:

1. **An outage longer than the lease.** The link (or the brain) comes back after more than `BODY_MOTION_TTL_S`;
   the body had stopped itself, and the brain's first renewal restarts it. The brain's confirmation gate still
   believed the motion was running, so nothing re-confirmed it.
2. **A renewal delayed on the network behind a STOP.** The brain's own ordering (`v1.8.2`) cannot control packets
   already in flight; a late `trot` could land after the STOP and restart the body.

## The fix: `renew` is its own verb

- Starting a motion returns a **`lease_id`** (`detail.lease_id`). The brain renews with
  `{action: "renew", params: {lease_id}}`.
- A `renew` can only **extend a lease that is still running** (same id, healthy, not past its deadline). It
  never touches the adapter and can never start a motion.
- If the lease is gone — expired, ended by a STOP, replaced by another motion, or a motion that failed to
  start — the body answers **`status: "lease_lost"`** with `detail.reason` (`expired`, `stopped`,
  `superseded`, `failed`, `unknown`) and does nothing. A `renew` that arrives after the deadline but before
  the body's watcher has run is refused too, rather than resurrecting the lease.
- `renew` is handled by the lease layer (`guarded_dispatch`), not by adapters, so no adapter changes. It is one
  more RPC on the `device_connect` body; `raw_zenoh` carries it on the existing action key.
- On the brain, a new `LeaseClient` (`pave_runtime/lease.py`) is the one place that knows how to renew; `run_live`
  and the `run_inference --allow-motion` hold both use it. On `lease_lost`, `run_live` emits
  `{"event": "lease_lost"}`, stops renewing, and **resets the confirmation gate**: the motion has to be confirmed
  again (`--confirmations` fresh observations) before it is restarted. No STOP is sent — the body already
  stopped, and a STOP could cancel another controller's motion. The hold in `run_inference` ends early.
- A reply that is **lost** (`no_reply`, transport error) is not `lease_lost`: the loop keeps renewing, as before.

A dedicated verb, rather than a flag on `trot`, is deliberate: a body older than this release answers an
unknown verb `unsupported` and does nothing, whereas an unknown flag on `trot` would just be run as a new
`trot`.

## Compatibility (the wire format is additive)

| Brain | Body | Behaviour |
|---|---|---|
| v1.8.5 | v1.8.5 | `lease_id` + `renew`; a late renewal is answered `lease_lost` |
| v1.8.5 | v1.8.2–v1.8.4 | the reply carries no `lease_id`, so the brain renews the old way (re-sending the motion) and `run_live` emits `{"event": "lease_legacy_body"}`. Works as before — **with the old weakness** |
| v1.8.2–v1.8.4 | v1.8.5 | the old re-send still renews a running motion, exactly as before — **with the old weakness** |
| v1.8.5 | body that starts answering `renew` with `unsupported` mid-run | downgraded to the legacy re-send (`renew_downgraded` event) |

The protection therefore needs **both sides on v1.8.5**. Upgrade the body (it is the safety-critical half) and
the brain together.

New in the per-tick/event JSON: `lease_lost`, `renew_downgraded`, `lease_legacy_body` events; `renew_mode`
(`lease_id` / `legacy`) in `run_inference`'s `motion_lease`; `lease_id` on the body's `lease_expired` event.

## Verification

- **256 tests** (218 before; +38), on Python 3.9 (Mac) and 3.12 (DGX), from a clean checkout of the tag.
- **Mutation-checked:** 14 separate reverts — no lease-id match, no expiry check, no `renew` interception, no
  health check, reused lease id, no `lease_id` in the reply, gate count not reset, gate not told, `lease_lost`
  read as a failure, no downgrade on `unsupported`, hold ignoring a lost lease, always-legacy request, `renew`
  missing from the `device_connect` RPCs — turn tests red for 13 of them. The fourteenth, dropping
  `lease.clear()` after `lease_lost`, is an equivalent mutant (the gate reset already stops the renewer); it is
  kept as explicit belt-and-braces.
- **Real `raw_zenoh`, same scenario on `v1.8.4` and `v1.8.5`** (mock body, `BODY_MOTION_TTL_S=3`, the brain frozen
  with `SIGSTOP` for 8 s mid-motion, then `SIGCONT`):

  | | `v1.8.4` body + brain | `v1.8.5` body + brain |
  |---|---|---|
  | brain frozen | body `STOP`s itself 3 s after its last renewal (≈1.9 s after the freeze) | same |
  | brain resumes | **first renewal restarts the body (`TROT`) with no decision in the brain's log** | `lease_lost` 0.05 s after the resume; **the body stays stopped** |
  | afterwards | body marches until the shutdown `STOP` | brain re-counts confirmations 1→4, then dispatches `trot` itself |

  The mixed pairs behave as the table above says: new brain + old body logs `lease_legacy_body` and restarts as
  before; old brain + new body restarts as before.
- Every doc claim was checked against the code (event names, flags, defaults).

**Still not verified:** a physical actuator or the real dog (the PuppyPi, Radxa and RPi 5 were unreachable when
this was built), a cross-host run of this change, and `device_connect`'s `serve()` against a live runtime —
only its RPC wiring is tested, with a stand-in for `device_connect_edge`.
**Known limits:** a crash of the body *process* is not covered (e.g. PuppyPi's `puppy_control` runs in its own
container and would keep marching); and with a pre-v1.8.5 brain or body the old weakness remains (see above).
