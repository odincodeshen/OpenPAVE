# OpenPAVE v1.8 Live Body

Status: experimental implementation

## Purpose

v1.8 connects the v1.7 headless inference/application pipeline to existing Physical AI data and
control paths:

```text
PuppyPi USB camera
-> HTTP/MJPEG over Wi-Fi (sensor data plane)
-> ObservationSource
-> InferenceRuntime
-> ApplicationRuntime
-> capability action
-> seam (control plane)
-> PuppyPi actuator
```

Image bytes do not travel inside `SeamTransport.send()`. The PuppyPi camera stream remains a
high-bandwidth data-plane input; the seam carries the resulting low-rate action.

## Observation Sources

The first observation source registry supports:

| Source | Input | Status |
| --- | --- | --- |
| `file` | Local JPEG/PNG | Implemented |
| `http_mjpeg` | HTTP JPEG/PNG snapshot or multipart MJPEG stream | Implemented, single frame |

`http_mjpeg` uses only the Python standard library. It reads the first complete JPEG from a stream,
applies a timeout and frame-size limit, and then closes the connection.

The current implementation is a single-observation workflow, not a persistent live inference loop.

## PuppyPi Camera Input

When PuppyPi publishes its USB camera through the previously validated `web_video_server` path, the
URL is normally:

```text
http://<puppypi-ip>:8080/stream?topic=/usb_cam/image_raw
```

OpenPAVE consumes the stream but does not currently install or launch `web_video_server`. Start the
existing PuppyPi camera publisher before running these commands.

First verify the stream from the DGX:

```bash
curl -I 'http://<puppypi-ip>:8080/stream?topic=/usb_cam/image_raw'
```

Then configure the inference backend:

```bash
export INFERENCE_RUNTIME=vllm_openai
export APPLICATION_RUNTIME=gesture_commander
export INFERENCE_API_BASE=http://127.0.0.1:8000/v1
export INFERENCE_API_KEY=EMPTY
export INFERENCE_MODEL=llava-hf/llava-v1.6-mistral-7b-hf
export PROMPT_PRESET=prompts/robot-commander-gesture.json
```

Capture one PuppyPi frame and run a safe dry-run:

```bash
python3 scripts/run_inference.py \
  --input-url 'http://<puppypi-ip>:8080/stream?topic=/usb_cam/image_raw'
```

The same URL can be supplied through config:

```bash
export OBSERVATION_URL='http://<puppypi-ip>:8080/stream?topic=/usb_cam/image_raw'
export OBSERVATION_TIMEOUT_SECONDS=10
export OBSERVATION_MAX_FRAME_BYTES=10485760

python3 scripts/run_inference.py
```

Expected observation fields include:

```json
{
  "media_type": "image/jpeg",
  "source": "http://<puppypi-ip>:8080/stream?topic=/usb_cam/image_raw",
  "bytes": 123456
}
```

## Reproduce end-to-end (run on hardware 2026-09-03)

The full chain was run on real hardware (graded Experimental in the matrix: one short run, TROT forced by a mock runtime) with a **static frame + `--seam`** (the `--input-url`
stream path above needs `web_video_server`, which OpenPAVE does not install). Hosts used: DGX brain
`192.168.0.24`, PuppyPi `192.168.0.6`, RPi5 camera `192.168.0.21`. Have the dog on the floor with
clear space before step 1 — it stands up.

**1. Bring up the PuppyPi body** — on `pi@192.168.0.6`, from `~/OpenPAVE`:

```bash
bash scripts/switch_puppypi_ros2.sh                                    # ROS 2 puppy_control + bridge (dog stands)
BODY_PYTHON=$HOME/.venv-dc/bin/python PUPPY_BRIDGE_HOST=127.0.0.1 \
  scripts/seam_run.sh configs/dgx-puppypi.env body                     # serve puppypi_bridge over raw_zenoh (:7447)
```

**2. Start vLLM on the brain** — on `odin@192.168.0.24`:

```bash
~/OpenPAVE/.venv/bin/vllm serve llava-hf/llava-v1.6-mistral-7b-hf \
  --host 0.0.0.0 --port 8000 --dtype float16 --max-model-len 3072 \
  --gpu-memory-utilization 0.55 --enforce-eager
```

**3. Capture one frame** from the RPi5 camera and copy it to the brain:

```bash
ssh odin@192.168.0.21 '~/.venv-zenoh/bin/python - <<PY
import cv2; c=cv2.VideoCapture(0)
for _ in range(12): c.read()          # warm up
_,f=c.read(); c.release(); cv2.imwrite("/tmp/gesture.jpg", f)
PY'
scp odin@192.168.0.21:/tmp/gesture.jpg /tmp/gesture.jpg     # then scp onto the DGX brain
```

**4. Run the pipeline to the real dog** — on the DGX, from `~/openpave`, with a zenoh-capable venv
(`~/.venv-zenoh`):

```bash
export SEAM_TRANSPORT=raw_zenoh ZENOH_CONNECT=tcp/192.168.0.6:7447
export INFERENCE_API_BASE=http://127.0.0.1:8000/v1 INFERENCE_MODEL=llava-hf/llava-v1.6-mistral-7b-hf

# safe first — force STOP over the seam (mock runtime, no vLLM needed) to confirm connectivity
$HOME/.venv-zenoh/bin/python scripts/run_inference.py --runtime mock --mock-output STOP --seam raw_zenoh

# full chain — real frame -> vLLM -> gesture_commander -> seam -> dog
$HOME/.venv-zenoh/bin/python scripts/run_inference.py \
  --runtime vllm_openai --input /tmp/gesture.jpg --seam raw_zenoh
```

`dispatch` returns `status: sent_over_seam`, and the body `state` is
`{"status": "completed", "detail": {"path": "bridge", "latency_ms": ...}}`. Measured over `raw_zenoh`:
STOP ~515 ms, TROT ~1013 ms (`path=bridge`) — matching the seam baseline in
[`docs/validation-matrix.md`](validation-matrix.md).

**Cleanup:**

```bash
ssh pi@192.168.0.6 'pkill -f "seam_cli.py serve"; docker stop puppypi_ros2'         # stop body, rest the dog
ssh odin@192.168.0.24 'pkill -9 -f "[v]llm serve"; pkill -9 -f "VLLM::EngineCore"'  # free the GPU (see note)
```

> **GPU gotcha:** `pkill vllm serve` alone can leave a `VLLM::EngineCore` child holding the GPU, so the
> next `vllm serve` fails with `Engine core initialization failed` / `init_device`. Always also kill
> `VLLM::EngineCore` (and any leftover `multiprocessing.resource_tracker`) before restarting.

## Safety Status

A single-shot `--seam` dispatch now has a **motion safety gate** (F1/F2):

- **Locomotion is blocked by default.** Motion verbs (`trot`, `move`) over `--seam` are refused — no
  connection, no send, `dispatch.status: "blocked"` — unless the operator opts in with
  `--allow-motion`. `stop` / `home` / `estop` always pass.
- **Motion is leased, not open-ended.** With `--allow-motion`, the CLI holds the motion for a bounded
  window (`--motion-hold-seconds`, default 3.0) and then **always issues an automatic STOP**,
  including on `Ctrl+C`, `SIGTERM`, `SIGHUP` (an SSH drop) or an error during the hold — so the body is
  never left marking time after the command exits. The lease covers the motion send itself, so a
  signal that lands mid-send still ends in a STOP.
- **The outcome drives the exit code (F3).** The payload carries an explicit `outcome`
  (`{ok, exit_code, kind}`), and `run_inference.py` exits with it: `0` ok, `3` dispatch failed
  (body `failed`/`rejected`/`unsupported`), `4` blocked by the gate, `5` safety-critical — a
  `stop`/`estop` (including the automatic lease STOP) did not complete. A body-side failure no longer
  exits `0`.
- **The action target is explicit (F4).** `--action-target <id>` (or env `ACTION_TARGET`) chooses which
  body the action goes to, and it is recorded in `dispatch.target`. The **sensor** side is already
  explicit (the `--input-url` / `OBSERVATION_URL`). For `device_connect` the target is the body's
  `DEVICE_ID`; when more than one body is discovered and no target is given, the send is **rejected**
  rather than driving the first one found. `raw_zenoh` is point-to-point (addressed by `ZENOH_CONNECT`)
  and ignores the target.

- **The body is its own last line of defence (dead-man lease).** Everything above is cleanup the *brain*
  performs, so none of it helps if the brain is gone — `kill -9`, a crash, power loss, or a dropped
  network leave nobody to send `STOP`, and a locomotion verb such as `trot` persists until one arrives.
  So the **body** keeps the clock: every `trot` / `move` it accepts carries a lease (`BODY_MOTION_TTL_S`,
  default **5 s**) and the body issues `STOP` **itself** if the lease is not renewed in time. Starting a
  motion returns a `lease_id`; the brain keeps the lease alive by sending a separate **`renew`** request
  carrying it (`{action: "renew", params: {lease_id}}`). A `renew` can only *extend* a lease that is still
  running — it never touches the adapter, so there is no gait hiccup, and it can never *start* a motion.
  If the lease is gone (it expired and the body stopped itself, a STOP ended it, another motion took
  over) the body answers `status: "lease_lost"` with `detail.reason` (`expired` / `stopped` /
  `superseded` / `failed` / `unknown`) and does nothing. So a renewal that arrives late — after an outage
  longer than the TTL, or delayed on the network behind a STOP — can no longer restart a motion that has
  ended. `run_live` renews every `--lease-renew-seconds` (default 2 s) from a dedicated task, so the lease
  tracks the brain's *liveness*, not how slow one inference is; on `lease_lost` it emits
  `{"event": "lease_lost"}`, stops renewing, and the motion must be **confirmed again** before it is
  restarted (no STOP is sent: the body already stopped, and a STOP could cancel someone else's motion). A
  single-shot `--allow-motion` hold renews during the hold and ends early on `lease_lost`. There is no
  brain-supplied TTL, so a buggy brain cannot ask for a longer one. `renew` is a lease-layer verb, not an
  adapter capability: both backends route it through `guarded_dispatch` (device_connect exposes it as one
  more RPC), so adapters need no change. **Compatibility:** a body older than v1.8.5 returns no `lease_id`
  (or answers `renew` with `unsupported`); the brain then falls back to the old renewal — re-sending the
  same motion, which still works but cannot detect a lost lease — and `run_live` says so once per motion
  with `{"event": "lease_legacy_body"}`. A pre-v1.8.5 brain talking to a v1.8.5 body behaves exactly as
  before. **Behaviour change (v1.8.2):** a one-shot `seam_cli.py send trot` is never renewed, so the
  body stops it after about the TTL instead of marking time until a `stop`; to hold a motion, use `run_live.py`
  or `run_inference.py --allow-motion --motion-hold-seconds N` (both renew). The lease is implemented once (`pave_runtime/lease.py`) and wraps
  both seam backends. Measured with a mock body over a real `raw_zenoh` link, after the brain was
  `kill -9`ed mid-motion: the body stopped itself **4.2 s** later on the DGX (same host) and **3.0 s**
  later from a DGX brain to a Raspberry Pi 5 over the LAN, and was not restarted. Expect **3–5 s**: the
  last renewal lands up to `--lease-renew-seconds` before the kill, so the body stops `TTL` after *that*
  — plus the time the body's own `stop` takes (about 0.5 s on a PuppyPi).
- **A body process being shut down also leaves its actuator safe.** `seam_cli.py serve` sends `stop` to
  its adapter on `SIGTERM` / `SIGHUP` / `Ctrl+C` (exit `128 + signal`; an unconfirmed stop exits `5`).

**Known limit:** the lease lives in the *body process*. If that process itself crashes or is `kill -9`ed,
nothing stops a controller that runs separately (PuppyPi's `puppy_control` keeps running in its own
container); covering that needs enforcement in the bridge/controller below the body process.
The `device_connect` backend shares the same lease code, but the lease logic is only tested through
`guarded_dispatch` and the `raw_zenoh` backend: `dc_seam.serve()`'s own wiring (the RPC handlers and the
expiry watcher) has no test and has not been run against a live Device Connect runtime.

The single-shot gate, outcome, and targeting are covered by `tests/test_seam_dispatch.py` (a fake
`SeamTransport` injected into `run_once`, plus a fake `device_connect_agent_tools`) — no zenoh, Device
Connect, or robot required. **Multi-observation confirmation is now provided by the live loop below.**

Keep camera-driven validation in dry-run or mock-dispatch mode, and drive a real body only with an
operator watching the robot.

## Live loop (multi-observation control)

`scripts/run_live.py` is the persistent driver: it repeats observe → infer → decide → **confirm** →
dispatch, and it owns the motion lifecycle — so locomotion is *confirmed over several frames* rather
than opted into per shot. It reuses the same observation / inference / application / seam plugins.

```text
loop:  ObservationSource.capture -> InferenceRuntime.infer -> ApplicationRuntime.decide
    -> confirmation gate -> edge-triggered seam.send(target) ;  watchdog + shutdown -> STOP
```

Safety model:

- **Confirmation.** A motion verb (`trot`/`move`) is dispatched only after it is decided on N
  consecutive observations within a window — `--confirmations` / `--confirmation-window-ms` (default
  from `TROT_CONFIRMATIONS` / `TROT_CONFIRMATION_WINDOW_MS`). `stop` / `home` / `estop` dispatch
  immediately.
- **Edge-triggered.** An action is *commanded* only when it changes, so a held `trot` is not re-issued
  to the adapter every tick. While a motion is active the loop only **renews** the body's lease
  (`--lease-renew-seconds`, default 2 s, well under the body's 5 s `BODY_MOTION_TTL_S`); a motion the
  body reports as failed is deliberately not renewed, so its lease STOPs it. Renewals and STOPs are
  serialized, so a renewal can never land after a STOP and restart the body, and a STOP **preempts** a
  renewal still waiting on the network instead of queueing behind it (a send to a dead link can take
  its full timeout).
- **A dispatch that did not arrive is sent again.** Edge-triggering must not mean "send once and hope":
  if a send gets no reply, a transport error, or a failed execution, the gate forgets it and the next tick
  offers it again (each tick's JSON carries `delivery`: `delivered`, `retry`, `abandoned`, or `refused`).
  A `STOP` is retried without limit; a motion verb is retried up to `--dispatch-retries` times (default 3)
  and then abandoned, and a definitive refusal (`rejected` / `unsupported`) is never retried. A transport
  exception is treated as a failed delivery rather than ending the loop. Because a motion send whose reply
  was lost may still have reached the body, such a motion keeps a `STOP` owed: it is sent when the loop next
  decides to stop and at shutdown, even though the gate does not believe the body is moving. On the body, a
  repeat of a motion that previously **failed** runs again — it is not mistaken for a renewal of a healthy
  one (`pave_runtime/lease.py`).
- **Watchdog.** If observe+infer stalls past `--motion-watchdog-ms` while a motion is active, the loop
  auto-STOPs; a watchdog STOP that is not confirmed stays owed and is retried on the next failing tick and
  at shutdown.
- **Fail-safe shutdown.** On `Ctrl+C`, `SIGTERM` (`kill`, a supervisor), `SIGHUP` (an SSH session
  dropping), an error, or a bounded run (`--max-ticks` / `--max-seconds`) finishing, the body is always
  sent `STOP`. Python only runs cleanup for `SIGINT` by default, so `pave_runtime/shutdown.py` turns
  all three signals into a clean shutdown (the exit code is `128 + signal`, e.g. `143` for `SIGTERM`);
  a second signal while the STOP is in flight is ignored so it cannot interrupt the STOP.
  `run_live` bounds its observation / inference calls with `pave_runtime.shutdown.bounded` rather than
  `asyncio.wait_for`, which on Python before 3.12 can swallow a cancellation and so lose the signal.
- **An unconfirmed STOP is loud.** If that final STOP does not complete, the driver exits `5`
  (safety-critical) instead of reporting success — the body may still be moving.

```bash
export INFERENCE_RUNTIME=vllm_openai INFERENCE_MODEL=llava-hf/llava-v1.6-mistral-7b-hf
export SEAM_TRANSPORT=raw_zenoh ZENOH_CONNECT=tcp/<puppypi-ip>:7447

python3 scripts/run_live.py \
  --input-url 'http://<puppypi-ip>:8080/stream?topic=/usb_cam/image_raw' \
  --action-target puppypi-01 --confirmations 2 --max-seconds 30
```

Each tick prints a compact JSONL record (`decided`, `confirm`, `dispatched`, `state`). The seam send
is per-call (a persistent brain session is a later optimization); the observation is re-captured each
tick. The confirmation gate and lifecycle are covered by `tests/test_live_loop.py` (scripted runtime +
fake seam — confirmation, window reset, edge-triggering, the stall watchdog, and shutdown STOP), with
no camera, model, or robot.
