# OpenPAVE v1.7 Inference/Application Runtime Plugin Specification

Status: implementation specification

Target branch: `feat/inference_plugin`

## 1. Objective

OpenPAVE v1.7 moves inference and application decisions out of the UI and into a headless
brain-side runtime. The UI is not part of the control path defined by this specification.

The minimum workflow is:

```text
static observation
-> inference runtime
-> inference result
-> application runtime
-> action proposal
-> capability validation
-> optional mock dispatch
```

This establishes the fourth OpenPAVE dimension without changing the validated baseline, seam
transport, robot adapters, or UI submodule.

## 2. Architectural Decision

OpenPAVE adopts a brain-side inference call point. Inference is not invoked by the UI.

The model backend and application decision are separate responsibilities:

- `InferenceRuntime` converts an observation and prompt into an `InferenceResult`.
- `ApplicationRuntime` converts an inference result into an `ActionProposal`.
- Capability normalization and adapter support checks happen after the proposal.
- Model output never bypasses validation to execute directly on a body endpoint.

## 3. v1.7 Scope

v1.7 implements:

- typed observation, inference request, inference result, and action proposal contracts
- `create_inference_runtime(name)` with lazy backend imports
- a dependency-free `mock` inference backend
- a dependency-free `vllm_openai` backend for static JPEG/PNG observations
- `create_application_runtime(name)`
- a fail-closed `gesture_commander` application
- prompt loading from the existing repository presets
- a headless CLI for a single observation
- dry-run by default and explicit mock-only dispatch
- unit and local integration tests

## 4. Out of Scope

The following work is deferred:

- DGX and physical PuppyPi validation
- live camera or sensor loops
- sensor data-plane plugins
- carrying JPEG bytes inside `SeamTransport.send()`
- multiple body endpoint routing
- streaming VLA policies or continuous action control
- UI changes or UI decoupling
- physical robot dispatch from the new CLI

The existing camera contract remains control/data-plane split: `get_image` metadata uses the
control plane, while frame bytes use a dedicated sensor data plane.

## 5. Runtime Contracts

### Observation

An observation contains:

- media type
- raw bytes
- source identifier
- timestamp
- optional metadata

### InferenceRequest

An inference request contains:

- observation
- prompt
- optional model name
- optional runtime options

### InferenceResult

An inference result contains:

- backend name
- model name when available
- model text
- optional structured output
- latency in milliseconds
- optional metadata

### ActionProposal

An action proposal contains:

- normalized action name
- parameters
- source application
- raw model output
- whether the safe fallback was applied
- optional reason

## 6. Plugin Registries

The inference registry follows the same lazy-import pattern as the seam transport registry:

```text
INFERENCE_RUNTIME=mock
APPLICATION_RUNTIME=gesture_commander
```

Core modules must have no optional inference backend dependencies. A selected backend imports
only its own requirements.

## 7. Gesture Commander Safety Rules

The first application accepts only exact, case-insensitive single-token outputs:

- `STOP` -> `stop`
- `TROT` -> `trot`

Leading and trailing whitespace is allowed. Extra words, punctuation, empty output, malformed
structured output, or unknown values fail closed to `stop`.

The resulting action must pass `normalize_action_payload` and the selected adapter must declare
the capability before dispatch.

## 8. Headless CLI

The CLI accepts a local observation and emits one structured JSON result. It defaults to dry-run.

Example:

```bash
python3 scripts/run_inference.py --mock-output TROT
python3 scripts/run_inference.py --mock-output TROT --dispatch --adapter mock
python3 scripts/run_inference.py --mock-output 'move forward'
```

The third command must produce the safe `stop` fallback. In v1.7 the CLI rejects dispatch to any
adapter other than `mock`.

Static-image validation against a running vLLM server:

```bash
export INFERENCE_RUNTIME=vllm_openai
export APPLICATION_RUNTIME=gesture_commander
export INFERENCE_API_BASE=http://127.0.0.1:8000/v1
export INFERENCE_API_KEY=EMPTY
export INFERENCE_MODEL=llava-hf/llava-v1.6-mistral-7b-hf
export PROMPT_PRESET=prompts/robot-commander-gesture.json

python3 scripts/run_inference.py --input /path/to/gesture.jpg
python3 scripts/run_inference.py --input /path/to/gesture.png --dispatch --adapter mock
```

The first command is a dry-run. The second runs the validated proposal only through the local mock
adapter; this increment still refuses physical adapter dispatch.

## 9. Configuration

The local profile uses:

```text
INFERENCE_RUNTIME=mock
APPLICATION_RUNTIME=gesture_commander
PROMPT_PRESET=prompts/robot-commander-gesture.json
MOCK_INFERENCE_OUTPUT=STOP
```

The `vllm_openai` backend uses:

```text
INFERENCE_API_BASE=http://127.0.0.1:8000/v1
INFERENCE_API_KEY=EMPTY
INFERENCE_MODEL=llava-hf/llava-v1.6-mistral-7b-hf
INFERENCE_TIMEOUT_SECONDS=30
INFERENCE_MAX_TOKENS=16
```

Existing `UI_API_BASE`, `UI_API_KEY`, and `UI_MODEL` variables are accepted as compatibility
fallbacks. New headless configurations should use `INFERENCE_*` names.

## 10. Testing and Acceptance

v1.7 local mock acceptance requires:

1. Registries reject unknown plugin names.
2. Inference backends are imported lazily.
3. Mock inference reports deterministic output and latency.
4. Gesture parsing maps exact `STOP` and `TROT` correctly.
5. Invalid output fails closed to `stop`.
6. Dry-run never invokes an adapter.
7. Explicit dispatch works with `MockAdapter`.
8. Physical adapters are rejected by the v1.7 CLI.
9. All existing OpenPAVE tests continue to pass.
10. JPEG and PNG requests match the OpenAI-compatible multimodal message format.
11. HTTP, connection, unsupported-media, empty-observation, and malformed-response failures are
    returned as inference runtime errors and never reach application dispatch.

## 11. Follow-on Validation

After local mock and HTTP contract acceptance, DGX validation will run:

```text
static JPEG/PNG -> DGX vLLM -> gesture application -> dry-run/mock -> PuppyPi
```

Physical validation must proceed in the order `STOP`, one `TROT`, then `STOP`, with an operator
able to stop the robot immediately.
